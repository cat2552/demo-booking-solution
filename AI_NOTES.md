## Использование ИИ в разработке проекта

В ходе реализации данного проекта я использовала Claude Code в качестве инструмента для ускорения написания шаблонного кода, проведения первичного аудита безопасности и улучшения качества документации и комментариев. Основные архитектурные решения и стратегия исправления ошибок принимались мной самостоятельно.

### 2. Опыт взаимодействия с ИИ и исправление ошибок
В процессе работы я зафиксировала несколько случаев, когда предложения ИИ были неоптимальными или ошибочными, что потребовало моего ручного контроля:

*   **Синтаксические ошибки:** В одном из этапов ИИ предложил исправление в `BookingController`, которое содержало синтаксическую ошибку (незакрытая фигурная скобка `{`). Я обнаружила это по `ParseError` в логах при запуске тестов.
*   **Неоптимальная архитектура:** ИИ изначально предлагал оставить бизнес-логику в контроллере или запросах (Request). Я внедрила Service Layer и Value Objects (`BookingInterval`), чтобы сделать систему масштабируемой (создание брони, в теории, может быть не только из самого запроса, а, например, из ивента, из результатов работы крона и т. д.) и избавить её от дублирования кода.
*   **Логические пропуски:** ИИ не заметил возможность создания брони в прошлом. Я самостоятельно выявила этот баг и ввела проверку `isPast()`. ТЗ формально не запрещает такие брони («других ограничений на даты нет»), поэтому в README это оформлено как осознанное отступление с обоснованием.
*   **Проблемы с типами данных:** Были попытки использовать некорректные методы приведения дат. Я скорректировала подход, переведя систему на `CarbonImmutable` и нормализацию к UTC.
*   **Защита от Race Condition: от «двойной защиты» к одному ограничению в БД.**
    1. **Первая версия.** ИИ предлагал решение только на уровне БД. Я реализовала защиту на двух уровнях: пессимистическую блокировку (`lockForUpdate`) комнаты в сервисе с проверкой `exists()` и триггер в PostgreSQL с той же блокировкой и проверкой как «последнюю линию обороны».
    2. **Пересмотр.** При ревью кода получилось упростить миграцию с триггером. Триггер заменили декларативным ограничением `EXCLUDE USING gist (room_id WITH =, tsrange(starts_at, ends_at, '[)') WITH &&)`: оно короче, не требует блокировок, а `[)` само разрешает встречи «впритык».
    3. **Неоптимальное предложение ИИ.** После замены триггера ИИ оставил в сервисе проверку `exists()` перед вставкой как «быструю проверку». Её убрали: сервис просто делает `INSERT` и превращает `SQLSTATE 23P01` в 409. Блокировка в коде тоже не нужна: ограничение защищает и при записи в обход сервиса.
    4. **Что ИИ сначала упустил.** Ошибка в PostgreSQL переводит текущую транзакцию в состояние «aborted», и все следующие запросы падают с `25P02`. Голый `INSERT` внутри внешней транзакции сломал бы её после 409. Проверили тестом (`assertDatabaseCount` после 409 падал) и обернули вставку в `DB::transaction`. Внутри чужой транзакции он ставит `SAVEPOINT`, это не блокировка.
    5. **Проверка тестов на «пустоту».** Чтобы убедиться, что новые тесты действительно ловят проблему, ограничение и `DB::transaction` временно отключали и смотрели, какие тесты падают.
    6. **Дополнительна проверка через апи.** Последней проверкой сталл запуск эндпоинтов из bookings.http, где последовательно выполнялись запросы по флоу.

### 3. Ручной контроль и верификация (Что не было доверено ИИ)

Несмотря на использование ИИ для рефакторинга кода и документации, я сознательно взяла на себя полный контроль над следующими критическими аспектами проекта, чтобы гарантировать качество и надежность итогового решения:

#### 3.1. Верификация работы API
Я не полагалась исключительно на автоматические тесты, сгенерированные ИИ. Каждый сценарий из файла `bookings.http` был проверен вручную через HTTP-клиент IDE. Это позволило убедиться, что:
*   Статус-коды (`201`, `409`, `422`, `403`) возвращаются в соответствии с бизнес-логикой.
*   Тела ответов (JSON) содержат корректные и понятные сообщения об ошибках.
*   API ведет себя предсказуемо при различных комбинациях входных данных.

#### 3.2. Управление состоянием инфраструктуры и БД
Весь процесс работы с базой данных контролировался вручную:
*   **Миграции:** Запуск, откат и проверка применения миграций (включая создание расширения `btree_gist` и ограничения `bookings_no_overlap`).
*   **Чистота данных:** Регулярный сброс состояния базы через `migrate:fresh` для исключения «загрязнения» данных между тестовыми прогонами.
*   **Проверка БД:** Ручная проверка ограничения `bookings_no_overlap` в PostgreSQL: пересекающаяся вставка в обход приложения отклоняется с `23P01`, встречи «впритык» и одинаковое время в разных комнатах проходят.

#### 3.3. Финальный аудит соответствия ТЗ
Я лично провела итоговую сверку поведения системы с требованиями технического задания, особенно в части работы с часовыми поясами (Москва и Новосибирск). Это было необходимо, чтобы убедиться, что алгоритм нормализации времени $\rightarrow$ UTC $\rightarrow$ Local Time работает безошибочно и пользователь из любого пояса получит корректный результат бронирования.

### 4. Роль ИИ в оформлении
ИИ использовался в качестве редактора для:
*   Формулирования понятных и профессиональных текстов ошибок для пользователя.
*   Структурирования `REVIEW.md` и `README.md` для обеспечения максимальной читаемости.
*   Коллегиального брейншторминга по разбору сложных кейсов.

**Итог:** Использование ИИ позволило сосредоточиться на проектировании архитектуры и поиске глубоких логических ошибок, сохранив при этом полный контроль над качеством и безопасностью итогового решения.
