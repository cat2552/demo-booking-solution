## API

Все методы требуют заголовки `Authorization: Bearer <токен>` и `Accept: application/json`. Без `Accept` запрос без токена вернёт 500 вместо 401.

| Метод | Адрес | Что делает |
|---|---|---|
| GET | `/api/bookings` | Мои брони (пагинация по 20) |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{id}` | Отменить бронь (только свою) |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

Пример (дата должна быть в будущем, иначе вернётся 422):

    curl -X POST http://localhost:8000/api/bookings \
      -H "Authorization: Bearer anna-token" \
      -H "Accept: application/json" \
      -H "Content-Type: application/json" \
      -d '{"room_id": 1, "title": "Планёрка", "starts_at": "2026-12-01T10:00:00+03:00", "ends_at": "2026-12-01T11:00:00+03:00"}'

Тело запроса `POST /api/bookings`:

| Поле | Тип | Обязательно | Примечание |
|---|---|---|---|
| `room_id` | integer | да | id существующей комнаты |
| `title` | string | да | до 255 символов |
| `starts_at` | string | да | ISO 8601 со смещением, см. ниже |
| `ends_at` | string | да | ISO 8601 со смещением, см. ниже |

Автор брони берётся из токена. Поле `user_id` в запросе не принимается: если его
прислать, оно игнорируется.

Больше примеров запросов, включая ошибочные, есть в `bookings.http`. Файл
можно запускать из PhpStorm или VS Code (REST Client).

Лог созданных броней пишется в `storage/logs/bookings.log`.

## Правила бронирования

Правила проверяются в `App\ValueObjects\BookingInterval` (вызывается из
`StoreBookingRequest::after()`) и в `App\Services\BookingService`.

| Правило | Где проверяется | Ответ |
|---|---|---|
| Брони одной комнаты не пересекаются, встречи «впритык» разрешены (условие `starts_at < new_end AND ends_at > new_start`) | ограничение `bookings_no_overlap` в БД, `BookingService` превращает ошибку в 409 | 409 |
| Длительность от 15 минут до 4 часов (`Booking::MAX_DURATION_MINUTES`) | `BookingInterval` | 422, поле `ends_at` |
| Начало и конец кратны 15 минутам (`Booking::STEP_MINUTES`), секунды равны 0 | `BookingInterval` | 422, поле `starts_at` |
| Бронь целиком в 09:00–20:00 по времени офиса комнаты (`Office::OPENS_AT` / `CLOSES_AT`) и не переходит через полночь | `BookingInterval` | 422, поле `starts_at` |
| Начало брони не в прошлом (допуск 1 минута). Осознанное отступление от ТЗ, см. ниже | `BookingInterval` | 422, поле `starts_at` |
| Отменить бронь может только её автор | `BookingController::destroy` | 403 |

Если для `starts_at` нарушено несколько правил сразу, возвращается одна ошибка
в таком порядке: прошлое, затем шаг 15 минут, затем рабочее время.

**Отступление от ТЗ: запрет брони в прошлом.** В задании сказано «Других
ограничений на даты нет», но бронь на прошедшее время всё равно запрещена.
Бронь нужна, чтобы занять переговорную на будущее. Бронь на прошедший интервал
ничего не резервирует, но такая запись показывалась бы в `index` и `today` как
настоящая. Скорее всего, это ошибка клиента: не та дата или не то смещение.
Поэтому лучше сразу вернуть 422 с понятным сообщением. Допуск в 1 минуту нужен,
чтобы не отклонять бронь «на сейчас» из-за расхождения часов клиента и сервера.
Если проверка всё-таки не нужна, её можно убрать: это метод
`BookingInterval::isPast()` и тест `test_cannot_book_in_the_past`.

## Коды ответов

| Код | Когда | Тело |
|---|---|---|
| 201 | Бронь создана | объект брони |
| 204 | Бронь отменена | пусто |
| 401 | Нет токена или он неверный (при `Accept: application/json`) | `{"message": "Unauthenticated."}` |
| 403 | Попытка отменить чужую бронь | `{"error": "Вы можете отменить только свои бронирования"}` |
| 404 | Бронь не найдена (`DELETE`) или комната не найдена (`today`) | `{"error": "Бронирование не найдено"}` / стандартный 404 Laravel |
| 409 | Комната занята на это время | `{"error": "Комната занята"}` |
| 422 | Ошибка валидации | `{"message": "...", "errors": {"поле": ["..."]}}` |
| 500 | Непредвиденная ошибка при создании | `{"error": "Server Error"}` |

Почему пересечение — это 409, а не 422. Запрос сам по себе корректен, но
конфликтует с текущим состоянием ресурса (слот уже занят). Тот же запрос мог бы
пройти минутой раньше. Это семантика `409 Conflict`. Ошибки 422 относятся к
самим данным запроса.

## Формат времени и таймзоны (строго)

`starts_at` и `ends_at` принимаются **только в ISO 8601 со смещением**:
`YYYY-MM-DDTHH:MM:SS±HH:MM` или `YYYY-MM-DDTHH:MM:SSZ`.
Дробные секунды синтаксически допускаются (`10:00:00.000+03:00`), но бронь
с ненулевыми секундами не пройдёт проверку шага 15 минут.
Смещение принимается в диапазоне от `-13:59` до `+13:59`.

Примеры валидных значений:

- `2026-12-01T10:00:00+03:00` — Москва (UTC+3)
- `2026-12-01T14:00:00+07:00` — Новосибирск (UTC+7)
- `2026-12-01T07:00:00Z` — то же, что 10:00 MSK

Примеры **невалидных** значений (вернут 422):

- `2026-12-01 10:00:00` — пробел вместо `T`, нет смещения
- `2026-12-01T10:00:00` — нет смещения (интерпретация «локально» запрещена:
  сервер не угадывает офис по комнате, смещение обязательно)
- `01.12.2026 10:00` — не ISO 8601
- `2026-12-01T10:00:00+25:00` — несуществующее смещение
- `2026-02-30T10:00:00+03:00` — несуществующая дата

На все ошибки формата возвращается одно сообщение:
`Время должно быть в формате ISO 8601 со смещением, например 2026-11-10T10:00:00+03:00`.

**Почему строго.** Офисы в разных таймзонах (Europe/Moscow и
Asia/Novosibirsk), и клиент может присылать время в любом смещении. Сервер
приводит значение к UTC (`CarbonImmutable::parse(...)->utc()`), а рабочие
часы 09:00–20:00 проверяет уже **в таймзоне офиса комнаты**
(`offices.timezone`), а не в таймзоне клиента. Без явного смещения в запросе
эту проверку нельзя сделать однозначно, поэтому смещение обязательно.

**Хранение.** Колонки `starts_at`/`ends_at` имеют тип `timestamp` (без зоны).
Приложение работает в `UTC` (`config/app.php`) и перед записью приводит
время к UTC, поэтому в БД всегда лежит UTC. При выдаче в JSON даты
сериализуются в ISO 8601 UTC с микросекундами, например
`2026-12-01T07:00:00.000000Z`. Фронт должен парсить их как UTC и сам
переводить в нужную таймзону. Исключение — `today`: он отдаёт готовую строку
`"time": "10:00 – 11:00"` уже в таймзоне офиса.

## Одновременные запросы (гонка)

Проблема: два одновременных `POST` на один слот оба выполняют проверку
пересечения, оба не видят чужую бронь (она ещё не закоммичена), и оба
вставляют запись.

Как решено. Гонку закрывает база данных декларативным ограничением
(миграция `add_booking_no_overlap_constraint`):

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
    EXCLUDE USING gist (room_id WITH =, tsrange(starts_at, ends_at, '[)') WITH &&);
```

- PostgreSQL сам гарантирует, что у одной комнаты нет двух строк
  с пересекающимися интервалами. Это работает для любых одновременных
  транзакций и любой записи в обход приложения.
- Полуоткрытый интервал `[)` разрешает встречи «впритык»: `[10:00, 11:00)`
  и `[11:00, 12:00)` не пересекаются.
- `btree_gist` нужен, чтобы использовать равенство по `room_id` в GiST-индексе.
  Расширение входит в стандартный образ `postgres:17`.

Отдельной проверки пересечения в коде нет. `BookingService` просто делает
`INSERT`. Если база отвечает `SQLSTATE 23P01` (нарушение ограничения), сервис
возвращает 409. Последовательные и одновременные запросы обрабатываются
одинаково.

Почему без проверки в коде. Проверка `exists()` перед вставкой не защищает
от гонки: между ней и `INSERT` всё равно есть окно. Вариантов было два.

- **Блокировка в коде (`SELECT ... FOR UPDATE` по комнате) без ограничения
  в БД.** Защищает только запись через этот сервис. Миграции, сидеры, другой
  код и ручные запросы её обходят. Запросы в одну комнату выстраиваются
  в очередь.
- **Ограничение в БД.** Защищает при любом способе записи и не требует
  блокировок. Правило задано одним выражением в одном месте.

Держать оба механизма незачем: блокировка в коде ничего не добавляет
к гарантии, которую уже даёт ограничение. Проверка `exists()` рядом
с ограничением тоже лишняя. Она дублирует правило пересечения (два места,
где может появиться расхождение, например в трактовке «впритык») и добавляет
лишний запрос. При этом гонку она не закрывает. Единственная её польза —
в обычном случае не доводить дело до ошибки в БД. Но ответ клиенту в обоих
случаях одинаковый (409), так что этот выигрыш не стоит дублирования.

Зачем `DB::transaction` вокруг одного `INSERT`. Это не блокировка. В PostgreSQL
любая ошибка внутри транзакции переводит её в состояние «aborted», и все
следующие запросы в ней падают с `25P02`. Если сервис вызвали внутри внешней
транзакции (в тестах это `RefreshDatabase`, в коде — любая обёртка), после 409
она стала бы непригодной. Вложенный `DB::transaction` в Laravel ставит
`SAVEPOINT`, и при ошибке откатывается только он. Без внешней транзакции это
обычная короткая транзакция на один `INSERT`.

Тесты:

- `test_cannot_overlap_bookings` — пересечение через API даёт 409, и после
  этого база доступна (проверка `SAVEPOINT`).
- `test_database_rejects_overlapping_booking_bypassing_service` — ограничение
  срабатывает при записи в обход сервиса.
- `test_database_allows_touching_bookings_and_other_rooms` — встречи «впритык»
  и одинаковое время в разных комнатах разрешены.

Проверено вручную. Если убрать ограничение, падают первый и второй тесты.
Если убрать `DB::transaction`, падает первый.

Как было раньше (см. историю коммитов). Сначала были и `lockForUpdate` по
комнате с проверкой `exists()` в сервисе, и триггер `BEFORE INSERT OR UPDATE`
на PL/pgSQL с той же блокировкой и проверкой. Правило пересечения было
записано дважды, блокировка тоже бралась дважды. Всё это заменило одно
ограничение.

## Интеграция с фронтендом

API stateless, авторизация — Bearer-токен (Sanctum). Фронт должен:

1. **Слать `Accept: application/json`** во всех запросах. Без него middleware
   `auth:sanctum` для гостя пытается построить редирект на маршрут `login`,
   а такого маршрута в API нет. Получается `RouteNotFoundException` и 500
   вместо 401. Ошибки в `api/*` уже рендерятся как JSON
   (`shouldRenderJsonWhen` в `bootstrap/app.php`), но код ответа всё равно
   неверный. Это поведение скелета, оно не исправлялось в рамках задания.
   Исправить можно в `bootstrap/app.php`: отключить редирект гостей для
   `api/*` (`$middleware->redirectGuestsTo(...)`) или отдельно отрендерить
   `AuthenticationException` в 401.
2. **Слать `Content-Type: application/json`** на `POST`.
3. **Токен** — в заголовке `Authorization: Bearer <токен>`. Токены из сидера
   (`anna-token`, `boris-token`) годятся только для локальной демонстрации;
   в проде токены выдаются через Sanctum.
4. **Время — только ISO 8601 со смещением** (см. раздел «Формат времени и
   таймзоны»). Фронт может слать время в таймзоне пользователя, сервер
   сам приведёт его к UTC.
5. **Обрабатывать 422** как ошибку валидации. Формат стандартный для Laravel
   `ValidationException`: `message` — первая ошибка, `errors` — массив
   сообщений по полям:

   ```json
   {
     "message": "Длительность бронирования должна быть от 15 минут до 4 часов.",
     "errors": {
       "ends_at": ["Длительность бронирования должна быть от 15 минут до 4 часов."]
     }
   }
   ```

6. **Обрабатывать 409** отдельно от 422: это не ошибка ввода, а занятый слот.
   Пользователю стоит показать «Комната занята» и предложить другое время.
   Формат тела другой: `{"error": "..."}`.
