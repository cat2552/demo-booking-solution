# Анализ исходного кода системы бронирования переговорных

## Критические уязвимости (Critical)
* **SQL-инъекции в BookingController::store**: Пользовательский ввод интерполировался напрямую в SQL-запросы, что позволяло выполнять произвольный код в базе данных.
* **Отсутствие авторизации при удалении**: Метод destroy удалял бронирование по ID без проверки авторства записи, что позволяло любому авторизованному пользователю удалить любую бронь в системе.
* **Ошибка в методе store**: Вызов `$request->validated('title')` приводил к ошибке 500, так как метод `validated()` возвращает массив всех данных, а не конкретное поле.

## Серьезные логические ошибки (Major)
* **Некорректная логика пересечений**: Использование операторов <= и >= запрещало бронирование «впритык», что противоречило требованиям ТЗ.
* **Игнорирование таймзон при проверке рабочих часов**: Валидация времени (09:00–20:00) выполнялась по времени сервера, а не по местному времени офиса, где находится комната.
* **Отсутствие базовых бизнес-правил**: Не была реализована проверка минимальной/максимальной длительности встречи и шага в 15 минут.
* **Race Condition (Состояние гонки)**: Проверка занятости комнаты и создание записи выполнялись как два раздельных шага. При одновременных запросах система позволяла создать две пересекающиеся брони на один слот.

## Архитектурные недостатки (Minor)
* **Раздутый контроллер (Fat Controller)**: Вся бизнес-логика была сосредоточена в контроллере, а существующий BookingService остался неиспользованныл.
